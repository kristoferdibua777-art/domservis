## Реализация и продуктовые границы

| Область | Текущее состояние | Следствие для следующей задачи |
| --- | --- | --- |
| Основная доска | CoffeeScript/Spine/ECO | Не искать её реализацию только в Vue |
| Mobile Vue | Маршрут перенаправляет на общую доску | Изменение неактивного компонента может не менять продукт |
| Песочница | Mock-данные и локальный state | Успешный сценарий не доказывает backend |
| PWA | Установка и уведомления | Offline CRUD и синхронизации нет |
| AI-ввод | Регулярные выражения | Это не LLM-интеграция |
| Каналы email/webhook/ai | Есть значения модели и задел intake | Наличие enum не означает готовый транспорт |
| Разделение по территориям/группам | В scope доски не реализовано | Не обещать изоляцию партнёров/бригад |
| Список доски | Запрашивается до 200 записей | Проверять масштаб и полноту выборки |
| Ticket sync | В основном DispatchJob → Ticket | Ticket не второй операционный редактор |
| Вложения | Собственный dispatch API | Полное зеркалирование в Ticket не гарантируется |

## Bootstrap и миграции

Некоторые миграции settings проверяют наличие system_init_done.
Первый Docker init выполняет migrations перед seeds.
Настройки Дом-Сервиса (dom_servis_dispatch_policy, Web Push) теперь создают и seeds; миграция
20261001120000_ensure_dom_servis_settings добавляет их системам, установленным раньше без них.
Описания полей backing ticket в ObjectManager на чистой установке по-прежнему добавляет шаг 7.3
руководства установки (колонки в tickets создаёт сама миграция).

Текущее руководство установки содержит дополнительный шаг.
Правильное дальнейшее исправление требует тестов clean install и upgrade,
а не только повторного запуска миграций на одной существующей базе.

## Целостность проекции

Ручное создание контроллером включает backing ticket в транзакции.
В обновлениях ошибка bridge не откатывает изменение DispatchJob. Заявка запоминает сбой
(ticket_sync_failed_at, ticket_sync_error), через 5 минут синхронизация один раз повторяется сама,
карточка на доске показывает предупреждение и кнопку «Повторить синхронизацию»
(POST /jobs/:id/resync_ticket), Dispatch Admin — число таких заявок. Успешная синхронизация снимает
отметку. Повтор переносит текущие поля заявки, но не восстанавливает пропущенную заметку об изменении.
Тикет может временно отставать от заявки; приём заявок из форм по-прежнему завершается ошибкой,
если тикет обновить не удалось.
Прямое создание модели вне сервисного потока также не даёт всей контроллерной семантики.

Backing ticket не несёт организацию партнёра.
Zammad держит организацию тикета равной организации клиента (check_default_organization).
Для ручной заявки используется реальный Customer User, найденный по точному нормализованному
телефону или созданный при отсутствии совпадения. Организация партнёра остаётся в DispatchJob
и попадает в текст заметки при создании тикета.

Нормализованный телефон пока не хранится в отдельной уникальной колонке. Resolver явно отклоняет
несколько legacy-пользователей с одним нормализованным номером, но не выполняет массовый backfill
и не объединяет записи автоматически.

## История заявки

DispatchEvent пишет старое и новое значение каждого изменённого бизнес-поля (формат — в [API](api.md#история-заявки)).
Старые события, записанные до этого, содержат только тип или частичные данные; backfill не выполняется.
Удаление заявки удаляет её историю (dependent: :destroy), а сами события на уровне модели не защищены
от изменения. Неизменяемый журнал и судьба истории при удалении — отдельное решение.
Карточка заявки на доске показывает короткую историю в режиме просмотра: строка на действие со временем
и автором, старые и новые значения раскрываются по клику. При открытом редактировании она не обновляется.

## Два смысла deadline_warning_minutes

- UI: порог предупреждения относительно времени визита.
- Фоновая задача: задержка после создания заявки в pool и после каждого возврата в pool (release, reopen),
  по умолчанию 120 минут; ещё не сработавшая задача при возврате переносится, а не дублируется.

Это не единая SLA-модель.
При возврате в pool мастера получают уведомление, а эскалация отсчитывается заново.

## Границы Scheduling Core v1

Core проверяет только канонические дату, точное время или существующее окно времени и соответствие
дня недели. Свободный текст времени из первичного intake сохраняется как snapshot, но его ручное
изменение уже требует канонического формата. Сервер не задаёт длительность визита, рабочие часы,
вместимость мастера или правила пересечений и не запрещает параллельные заявки.

## Календарь диспетчера v1

Режим «Календарь» на доске (диспетчер и администратор, не мобильная раскладка) показывает один день:
колонку заявок без мастера и по колонке на каждого мастера. Правила приняты 2026-09-28:

- точное время HH:MM — визит заданной длительности (по умолчанию 2 часа), окно HH:MM-HH:MM
  берётся как есть;
- сетка на заданные часы (по умолчанию 08:00–20:00), заявки вне этих часов и без канонического
  времени (пустое или текст intake) перечислены под колонкой;
- «сегодня» и линия текущего времени считаются в часовом поясе timezone_default Zammad;
- пересечения заявок одного мастера только подсвечиваются, назначение не блокируется.
  В карточке заявки при выборе мастера показываются его пересекающиеся визиты этого дня,
  а занятые мастера помечены в списке «занят в это время».

Календарь запрашивает у сервера все заявки выбранного дня (GET /jobs?visit_date=…), пока ответа нет,
показывает то, что уже загрузила доска. Отменённые и переданные партнёру заявки не показываются.
Окно, конец которого не позже начала, показывается как визит заданной длительности.

Длительность визита (15–720 минут) и часы сетки (начало 0–23, конец 1–24) задаются в Dispatch Admin
и хранятся в настройках политики (visit_duration_minutes, calendar_day_start_hour,
calendar_day_end_hour в dom_servis_dispatch_policy). Значение вне границ заменяется значением по
умолчанию; если конец дня не позже начала, оба часа возвращаются к 8 и 20. Доска применяет настройки
при загрузке политики: при открытии доски и при ручном обновлении. Сервер эти настройки только хранит:
длительность и часы по-прежнему не проверяются при сохранении заявки.

## Уведомления

Получатели выбираются по разрешениям, а не по территории/организации заявки.
HTTP success тестового push означает enqueue, а не доставку.
Сбой провайдера, истёкшая подписка, права ОС и остановленный scheduler требуют отдельных проверок.

## Качество и покрытие

Есть модельные, request и service-тесты Дом-Сервиса.
Request-тесты назначения мокают backing ticket.
Полного покрытия реального мобильного PWA/push-потока из наличия этих тестов не следует.

Большие файлы dispatch_board.coffee и dom_servis_dispatch.css концентрируют UI-логику.
Рефакторинг оправдан конкретной задачей и сценариями регрессии;
не совмещать его без необходимости с изменением бизнес-поведения.

## Работа с upstream

Форк остаётся на мартовской базе Zammad.
Проверка GitHub 2026-09-05 показывала отставание develop на 1410 коммитов;
число историческое и должно пересчитываться перед задачей обновления.

Сравнивать с текущим upstream после fetch.
Не вычислять точку расхождения только по датам: локальная копия может быть shallow.

Перед merge проверять интеграционные изменения в User, формах, mobile detection,
seeds/settings, зависимостях и Docker-сборке.

## Что документация не подтверждает

- Какой образ реально работает на сервере заказчика.
- Что DNS, SMTP, Web Push и backups настроены именно там.
- Производительность под конкретной нагрузкой.
- Успешную установку на новом VPS в ходе написания документации.

Эти факты получают проверкой соответствующего окружения и записывают в отчёт приёмки.
